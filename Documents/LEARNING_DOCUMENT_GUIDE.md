# 학습 문서 작성 규칙

이 문서는 `Documents/Curriculum/`에 생성하는 과정별 학습 문서의 작성 기준을 정리합니다. 새 강의 노트, 보충 자료, 퀴즈 문서, 실습 안내를 만들 때 이 문서를 우선 참조합니다.

## 기본 원칙

1. 대상 독자는 프로그래밍 입문자와 게임 개발 지망생입니다.
2. 설명은 추상 용어를 먼저 던지기보다 실생활 비유로 감각을 잡은 뒤 정확한 용어로 연결합니다.
3. C# 코드 설명은 `위->아래`, `오->왼`, `안->밖` 순서로 읽는 흐름을 자주 드러냅니다.
4. 학생이 직접 타이핑할 수 있는 짧고 완성 가능한 예제 코드를 우선합니다.
5. 문서는 수업 중 바로 읽고 따라 할 수 있도록 큰 개념, 예제, 실습, 확인 질문의 순서로 구성합니다.
6. 과정 일정, 일수, 과목 배치는 `Documents/COURSE_SCHEDULE_SUMMARY.md`를 최우선 기준으로 삼습니다.

## 파일명과 위치

1. 과정별 학습 문서는 기본적으로 `Documents/Curriculum/` 아래에 생성합니다.
2. `Documents/Curriculum/` 아래에는 과정 번호와 과정명을 조합한 폴더를 만듭니다. 예: `01.CSharpBasic`
3. 과정 폴더 안에 일차별 학습 문서를 생성합니다.
4. 새 파일명에는 날짜나 시간 접미사를 붙이지 않습니다.
5. 일자별 문서는 `DAY##_영문키워드.md` 형식을 사용합니다.
6. C# 기초 과정은 `DAY01_CS_BASICS_METHODS.md`처럼 `DAY번호_CS_주제키워드` 형식을 우선 사용합니다.
7. 보충 개념 문서도 가능하면 해당 과정 폴더 안에 배치하고, 특정 과정에 속하지 않는 공통 가이드만 `Documents/`에 둡니다.
8. 기존 날짜 접미사가 붙은 문서는 레거시 파일로 보고, 새 문서를 만들 때 그 형식을 따라가지 않습니다.

예시:

```text
Documents/Curriculum/01.CSharpBasic/DAY01_CS_BASICS_METHODS.md
Documents/Curriculum/01.CSharpBasic/DAY02_CS_CONTROL_FLOW.md
Documents/Curriculum/01.CSharpBasic/DAY03_CS_CLASSES_OBJECTS.md
Documents/LEARNING_DOCUMENT_GUIDE.md
```

## 일자별 DAY 문서 구조

DAY 문서는 다음 흐름을 기본 골격으로 사용합니다. 주제 성격에 따라 섹션명을 조금 바꿀 수 있지만, 학습 흐름은 유지합니다.

````md
# DAY ##: 주제명

오늘의 목표 문단

## 1. 핵심 개념: "입문자가 잡을 수 있는 비유"

개념 설명

### 이 단어는 무슨 뜻인가요?

- **용어**: 쉬운 정의

### 실습 예제: 예제 제목

**미션:** 학생이 할 일을 한 문장으로 설명합니다.

<details>
<summary>코드 보기</summary>

```csharp
// 완성 가능한 예제 코드
```

</details>

### 실행해보면

예상 출력 또는 관찰 포인트

### 생각해보기

1. 확인 질문
2. 응용 질문

## 오늘의 정리

- 핵심 요약
- 다음 수업과의 연결
````

## 설명 방식

1. 처음 등장하는 개념은 비유, 정확한 정의, 코드 적용 순서로 설명합니다.
2. 용어 설명은 `### 이 단어는 무슨 뜻인가요?` 섹션을 사용하고, 굵은 용어 뒤에 쉬운 문장으로 풀이합니다.
3. 코드 블록 전에는 학생이 무엇을 확인해야 하는지 미션을 먼저 제시합니다.
4. 코드 블록 안 주석은 너무 길게 쓰지 않고, 입문자가 헷갈릴 줄만 짚습니다.
5. 예제는 Console Application에서 바로 실행 가능한 형태를 우선합니다.
6. 수업 분위기에 맞게 게임 캐릭터, 몬스터, 아이템, 인벤토리, 맵 같은 소재를 적극 활용합니다.

## 실습 예제 규칙

1. 예제 코드는 가능한 한 `using System;`, `namespace`, `Program`, `Main`을 포함한 완성형으로 제공합니다.
2. 학생이 따라 치기 어렵지 않도록 한 예제는 하나의 핵심 개념에 집중합니다.
3. `Console.WriteLine`, 입력, 조건문, 반복문, 클래스 등은 수업 진도에 맞춰 사용합니다.
4. 아직 배우지 않은 문법을 써야 할 경우, 짧은 주석이나 Tip으로 이유를 설명합니다.
5. 코드가 길어질 때는 `<details>`와 `<summary>코드 보기</summary>`로 접어 둡니다.

## 퀴즈와 확인 질문

1. DAY 문서 끝에는 짧은 확인 질문이나 생각해보기 질문을 둡니다.
2. 별도 정답지는 `QUIZ_ANSWERS_*.md` 계열 문서의 형식을 따릅니다.
3. 정답 문서는 일차별 제목 아래에 번호 목록을 두고, 각 문항에 `정답`과 필요한 해설을 붙입니다.
4. 주관식 문항은 `(학생의 주관적 답변)`처럼 정답 범위를 명시합니다.

## Markdown 스타일

1. 강조(`**`)와 큰따옴표(`"`)가 함께 쓰일 때는 강조 기호를 따옴표 안쪽에 배치합니다. 예: `"**강조문구**"`
2. 강조 기호가 소괄호 등 특수기호와 붙어 렌더링이 깨지지 않도록 공백을 둡니다. 예: `**단어** (설명)`
3. 코드, 파일명, 명령어, 키워드는 백틱으로 감쌉니다.
4. 정교한 도식이나 겹침 표현이 필요하면 별도 `.svg` 파일로 저장하고 Markdown 이미지 태그로 삽입합니다.
5. SVG는 표준 SVG 네임스페이스를 포함하고, 다크/라이트 테마 모두에서 보이는 고대비 색상을 사용합니다.

## 참조 우선순위

1. `Documents/COURSE_SCHEDULE_SUMMARY.md`: 과정 일정, 일수, 과목 배치.
2. `26국기_교수계획서.pdf`: 공식 강의 계획 및 일정표.
3. `Documents/HISTORY.md`: 변경 이력과 최근 작업 맥락.
4. 기존 `Documents/DAY*.md`: 레거시 수업 문서의 톤과 예제 구성.
5. `Code/DayXX/`: 해당 일차의 실습 코드.

## NCS 평가 준거 반영 원칙

1. `NCS_Modules/`의 각 교재에 포함된 평가 준거와 평가 방법을 최대한 존중합니다.
2. 학습 문서의 목표, 실습, 포트폴리오, 평가 문항은 해당 NCS 교재의 평가 준거와 연결되어야 합니다.
3. NCS 교재의 기술 스택이 Unity 6 수업 흐름과 다를 경우, 평가 의도는 유지하되 구현 환경과 예시는 Unity 6 기준으로 재구성합니다.
4. 평가 준거를 단순히 복사하지 않고, 학생이 Unity 6 프로젝트 안에서 관찰 가능한 행동과 산출물로 바꿔 제시합니다.
5. 과정별 문서를 만들기 전 해당 NCS 교재에서 다음 항목을 먼저 확인합니다.
   - 능력단위명
   - 능력단위 요소
   - 수행준거 또는 평가 준거
   - 평가 방법
   - 지식, 기술, 태도 항목

## Unity 6 기반 재구성 원칙

1. 학습 문서와 실습 예제는 최신 Unity 6 환경을 기준으로 작성합니다.
2. NCS 교재의 예제가 특정 엔진, DirectX, 서버, 웹, DB 기술에 치우쳐 있더라도 수업에서는 Unity 6에서 구현 가능한 형태로 변환합니다.
3. Unity 6의 씬, GameObject, Component, Prefab, ScriptableObject, Physics, Coroutine/async, Addressables, URP 등은 교과목 성격과 학습 시간에 맞는 범위에서만 사용합니다.
4. UI는 기본적으로 UGUI(Unity UI)를 사용합니다. 별도 지시가 없는 한 UI Toolkit을 기준으로 학습 문서나 평가 과제를 만들지 않습니다.
5. 입력 처리는 기본적으로 Input System 패키지를 사용합니다. 별도 지시가 없는 한 Legacy Input Manager 기준으로 학습 문서나 평가 과제를 만들지 않습니다.
6. UGUI와 Input System을 함께 쓰는 예제는 학생이 Unity 6 프로젝트에서 바로 따라 할 수 있도록 필요한 GameObject, Component, Input Action 구성 단계를 명시합니다.
7. Unity 컴포넌트를 중심으로 수업을 구성하는 경우, 해당 컴포넌트의 Inspector 주요 프로퍼티를 표로 정리하고 각 값이 실행 결과에 미치는 영향을 함께 설명합니다.
7. 고급 기능은 NCS 평가 준거 달성에 꼭 필요한 경우에만 포함하고, 입문자가 학습 시간 안에 완성 가능한 작은 단위로 쪼갭니다.
8. 포트폴리오와 평가자 체크리스트 문제는 Unity 6 프로젝트에서 직접 실행하거나 확인할 수 있는 산출물을 기준으로 설계합니다.

## 과정별 평가 산출물 규칙

각 교과목 또는 능력단위별 학습 문서를 만들 때 평가 방법은 NCS 교재의 평가 방법을 따르되, 기본 산출물은 다음 3종으로 구성합니다.

1. 서술형 시험
2. 포트폴리오
3. 평가자 체크리스트 확인 문제

평가 산출물은 학생 공개용 GitHub에 노출하지 않습니다. 공개 학습문서에는 `Documents/Exam/` 내부 경로, 실제 시험 문항, 정답, 채점 기준, 평가자 체크리스트 세부 항목을 직접 적지 않습니다. 이런 내용은 `.gitignore`로 제외된 `Documents/Exam/` 아래에만 작성합니다.

### 서술형 시험

1. 교과목별 서술형 시험은 10문제로 구성합니다.
2. 문제는 NCS 평가 준거를 확인할 수 있도록 개념 이해, 절차 설명, Unity 6 적용 판단, 오류 원인 분석을 고르게 포함합니다.
3. 단순 암기보다 “왜 그렇게 구현해야 하는지”, “Unity 6에서는 어떤 오브젝트/컴포넌트/스크립트로 확인할 수 있는지”를 묻습니다.
4. 정답 또는 채점 기준은 별도 문서에 함께 작성합니다.

### 포트폴리오

1. 포트폴리오는 학습 내용과 배정 학습 시간 안에 완성 가능한 범위로 제한합니다.
2. 결과물은 Unity 6 프로젝트, 씬, 프리팹, 스크립트, 데이터 파일, 캡처 이미지, 짧은 구현 설명 중 필요한 조합으로 구성합니다.
3. 포트폴리오 주제는 NCS 평가 준거를 보여줄 수 있어야 하며, 지나치게 큰 게임 완성 과제로 확장하지 않습니다.
4. 평가 기준은 기능 동작, 코드 구조, Unity 오브젝트 구성, 사용자 조작 흐름, 제출 산출물 확인 가능성을 중심으로 작성합니다.

### 평가자 체크리스트 확인 문제

1. 평가자 체크리스트를 확인할 수 있는 실기형 문제 1개를 별도로 만듭니다.
2. 이 문제는 평가자가 체크리스트 항목을 보며 직접 확인할 수 있도록 관찰 포인트를 명확히 둡니다.
3. 문제는 Unity 6 프로젝트에서 실행 가능한 작은 과제로 구성합니다.
4. 체크리스트 항목은 `완료`, `부분 완료`, `미완료`처럼 평가자가 표시하기 쉬운 형태로 작성합니다.

## 평가 산출물 폴더 규칙

평가 산출물은 학습 문서와 분리하여 별도 폴더에 생성합니다. 기본 위치는 `Documents/Exam/`입니다.

```text
Documents/Exam/
  02.Algorithm/
    WRITTEN_TEST.md
    PORTFOLIO_ASSIGNMENT.md
    CHECKLIST_TASK.md
```

각 파일의 역할은 다음과 같습니다.

| 파일 | 내용 |
| :--- | :--- |
| `WRITTEN_TEST.md` | 서술형 시험 10문제와 정답/채점 기준 |
| `PORTFOLIO_ASSIGNMENT.md` | 학습 시간 안에 가능한 Unity 6 포트폴리오 과제와 제출 기준 |
| `CHECKLIST_TASK.md` | 평가자 체크리스트 확인용 실기 문제 1개와 체크 항목 |

평가 산출물의 과정 폴더명은 학습 문서의 과정 폴더명과 일치시킵니다. 예: `Documents/Curriculum/02.Algorithm/`의 평가 산출물은 `Documents/Exam/02.Algorithm/`에 둡니다.

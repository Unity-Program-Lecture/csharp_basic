# DAY 13: 게임 서버 응용, 데이터, 리포트, 패치

오늘은 실시간 플레이 서버가 데이터 저장·운영 기록·클라이언트 업데이트와 어떻게 연결되는지 설계합니다.

## 1. 핵심 개념: "경기 진행표, 기록 보관소, 안내 방송"

- **데이터베이스 (Database, DB)**: 게임 계정, 점수, 보상처럼 오래 보관할 데이터를 관리하는 저장소입니다.
- **리포팅 (Reporting)**: 운영자가 접속 수, 오류, 게임 결과 같은 상태를 확인할 수 있게 기록·정리하는 기능입니다.
- **패치 (Patch)**: 이미 설치된 게임 클라이언트에 수정 파일이나 버전 정보를 배포하는 과정입니다.
- **경계 (Boundary)**: 실시간 판정, 영구 저장, 화면 표시처럼 책임이 다른 부품을 나누는 선입니다.

## 2. 안내형 실습: 코인 게임 데이터 흐름 문서

**미션:** DAY11 코인 게임의 실시간 처리와 저장 처리를 구분합니다.

1. 아래 표를 문서에 복사합니다.

| 상황 | 즉시 처리 담당 | 저장 담당 | 운영 기록 |
| :--- | :--- | :--- |
| Player가 코인에 닿음 | Game Server가 거리·중복 확인 | 게임 종료 또는 저장 시 DB에 Score 기록 | `CoinCollected` 횟수 |
| Client 접속 실패 | 접속 모듈이 실패 반환 | 저장하지 않음 | 실패 시각·오류 코드 |
| 새 버전 배포 | Patch 서버가 버전 비교 | 파일 목록·버전 정보 관리 | 적용 성공·실패 수 |

2. `PlayerId`, `Score`, `LastSavedAt` 세 필드를 가진 Score 저장 구조를 설계합니다.
3. 실시간 이동 위치를 매 프레임 DB에 저장하지 않는 이유를 두 가지 적습니다.
4. `v1.0.0`과 `v1.0.1`의 패치 목록 예시를 작성합니다.

### 완료 확인

- [ ] Server 판정과 DB 저장의 책임을 구분했다.
- [ ] 운영자가 확인할 오류 또는 접속 기록을 하나 이상 정했다.
- [ ] 패치에는 버전 비교와 파일 목록이 필요함을 적었다.

## 응용 실습: 접속 리포트

Host 시작, Client 연결, Client 종료 세 상황에 대해 남길 로그 형식을 설계하세요. 각 로그에 시간, 이벤트 이름, Client 식별값을 포함하세요.

## 오늘의 정리

- 게임 서버 응용 프로그램은 실시간 동기화만이 아니라 저장, 운영 관찰, 업데이트까지 연결합니다.

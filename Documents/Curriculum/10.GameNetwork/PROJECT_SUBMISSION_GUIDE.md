# 게임 네트워크 프로그래밍 결과물 제출 안내

## 1. 과제 목표

**NGO 코인 게임과 UDP 피어 통신 프로그램을 하나의 제출 묶음으로 준비하세요.** 두 프로그램을 하나로 합칠 필요는 없습니다. 수업에서 배운 내용을 활용하되, 완성 코드의 모양이 아니라 실제 기능과 설계 이유를 확인합니다.

제출 기한과 제출 위치는 별도 공지를 확인하세요. 아래 요구사항을 충족하는 범위에서 코드 구조·화면 배치·메시지 형식은 직접 정하세요. 이 문서는 요구사항 안내이며 완성 코드나 구현 순서는 제공하지 않습니다.

## 2. 공통 개발 조건

- Unity 프로젝트는 수업 지정 Unity 6 버전과 NGO 2.13.3을 사용하세요. 다른 패키지는 [환경 설정 안내](ENVIRONMENT_SETUP_GUIDE.md)의 수업 지정 버전을 사용하세요.
- Unity의 전송 계층은 Unity Transport를 사용하세요.
- Unity 입력은 Input System, 화면은 UGUI를 사용하세요. 필수 기능을 확인할 수 있는 간단한 화면이면 충분합니다.
- UDP 프로그램은 수업 지정 .NET SDK를 사용하는 C# 콘솔 프로젝트로 작성하세요.
- 두 과제 모두 같은 컴퓨터에서 실행·검증할 수 있게 준비하세요. 외부 서버·유료 서비스·공유기 설정 없이 실행할 수 있어야 합니다.
- 수업 코드와 참고 자료를 활용할 수 있습니다. 활용한 부분과 직접 추가·수정한 부분을 구분해 기록하고, 본인의 코드가 어떻게 동작하는지 설명할 수 있어야 합니다.
- 그래픽 품질이나 게임의 크기보다 통신·판정·동기화의 정확성을 우선하세요. 구현하지 못한 기능은 숨기지 말고 현재 상태와 제한 사항을 적어 주세요.

## 3. 과제 A: NGO 코인 게임

### 게임 구성과 접속

- **Host** 와 **Client** 를 각각 시작할 수 있어야 합니다.
- 같은 컴퓨터에서 Host와 Client를 동시에 실행해 두 참여자의 플레이를 확인할 수 있어야 합니다.
- 접속 주소와 포트를 확인할 수 있게 하고, 실행 방법에 사용할 값을 기록하세요.
- 각 참여자에게 플레이어가 생성되고 본인에게 배정된 플레이어만 직접 조작할 수 있어야 합니다.
- 플레이어는 CharacterController를 사용해 이동하도록 구현하세요. 이동 결과는 상대 실행 화면에서도 확인할 수 있어야 합니다.

### 코인 획득과 서버 판정

- 여러 코인을 배치하고 플레이어가 획득을 요청할 수 있게 하세요.
- Client가 자신의 점수나 코인 제거를 최종 확정하지 않도록 하세요. 서버가 요청의 유효성을 확인한 뒤 결과를 결정해야 합니다.
- 잘못된 코인 식별값, 획득할 수 없는 거리, 이미 획득한 코인에 대한 요청을 서버가 거절하도록 하세요.
- 두 참여자가 같은 코인을 획득하려고 해도 보상이 중복으로 지급되지 않아야 합니다.
- 정상 요청과 잘못된 요청을 확인할 방법을 준비하세요. 테스트용 입력이나 별도 시험 기능을 사용할 수 있으며, 시험 방법을 문서에 기록하세요.

### 공유 상태와 화면

- 확정된 점수와 남은 코인 상태가 Host와 Client 양쪽에서 일치해야 합니다. 개인별 점수와 공동 점수 중 사용할 방식을 직접 정하고 문서에 명시하세요.
- 코인이 획득되면 두 실행 화면에서 같은 코인이 제거되거나 획득 불가 상태로 바뀌어야 합니다.
- 현재 점수와 접속 상태를 화면에서 확인할 수 있어야 합니다. 접속 중에는 중복 시작을 막고 실패 시 다시 시도할 수 있어야 합니다.
- Client가 종료돼도 Host는 계속 실행되어야 합니다. Client가 다시 접속하면 현재 점수와 남은 코인 상태를 받을 수 있어야 합니다. 재접속한 참여자의 개인 점수 유지 여부는 직접 정하고 제한 사항에 적어 주세요.
- 입력·통신 요청·서버 판정·상태 반영·화면 표시의 역할을 구분하세요. 특정 클래스 개수나 파일 이름을 강제하지는 않습니다.

## 4. 과제 B: UDP 피어 통신

### 동기화할 데이터: 피어별 2차원 위치

**각 피어가 가진 가상 플레이어의 2차원 위치 `(X, Y)`를 서로 전송하고, 상대의 최신 위치를 콘솔에 표시하세요.** 채팅 메시지만 주고받거나 받은 문자열을 출력하는 것만으로는 완료되지 않습니다. Unity 화면이나 실제 캐릭터는 만들지 않아도 됩니다.

- 두 피어는 서로 다른 식별값을 사용하세요. 각 피어는 자신의 위치만 입력·변경하고 상대 피어에게 전송합니다.
- X와 Y는 정수로 입력할 수 있게 하세요. 키 입력으로 한 칸씩 움직이거나 좌표를 직접 입력하는 방식 중에서 선택할 수 있습니다.
- 위치를 바꾸면 변경된 자신의 위치를 전송하세요. 수신을 기다리느라 자신의 위치 입력·송신이 계속 막혀서는 안 됩니다. 특정 스레드·비동기 구현 방식을 강제하지는 않습니다.
- 수신 측은 받은 위치를 해당 송신 피어의 상태로 보관하고 화면에 반영하세요. 상대의 위치를 자신의 위치로 덮어쓰지 마세요.
- 두 피어의 좌표를 같은 값으로 만드는 과제가 아닙니다. 피어 A의 위치를 B가 확인하고, 피어 B의 위치를 A가 확인하는 과제입니다.

### 위치 메시지에 포함할 데이터

| 항목 | 요구사항 |
| --- | --- |
| 송신 피어 식별값 | 누구의 위치인지 구별할 수 있어야 합니다. |
| 순서 번호 | 각 피어가 위치 메시지를 새로 보낼 때 증가하는 정수 값을 포함하세요. |
| X 좌표 | 송신 피어의 현재 X 위치를 포함하세요. |
| Y 좌표 | 송신 피어의 현재 Y 위치를 포함하세요. |

필드 이름·배치·구분자·직렬화 형식은 직접 정하고 `DESIGN.md`에 기록하세요. 좌표가 바뀌어 새 메시지를 만들 때마다 순서 번호를 증가시키고, 오래된 메시지 시험에서는 당시의 번호와 좌표를 그대로 사용하세요. 번호 순환이나 UDP 프로그램 재시작 후의 상태 복구는 필수 조건이 아닙니다.

### 통신과 메시지 규약

- 두 콘솔 프로그램을 실행해 서로 데이터를 보내고 받을 수 있게 하세요. 같은 프로그램을 서로 다른 설정으로 두 번 실행하는 방식도 가능합니다.
- 로컬 주소·포트와 상대 주소·포트를 설정할 수 있어야 합니다. 같은 컴퓨터의 두 프로그램이 서로의 수신 포트를 충돌 없이 사용하도록 하세요.
- 위 네 항목을 포함하는 위치 메시지 규약을 직접 정하세요.
- 콘솔에서 자신의 식별값·현재 위치, 상대의 식별값·마지막으로 반영한 위치와 순서 번호를 확인할 수 있어야 합니다. 상대 데이터가 아직 없으면 미수신 상태를 표시하세요.
- 빈 메시지, 잘못된 형식, 해석할 수 없는 값이 들어와도 프로그램 전체가 비정상 종료되지 않도록 하세요.

### 상태 처리와 관찰

- 송신 피어별로 최신 위치를 관리하고, 이미 반영한 순서 번호보다 작거나 같은 메시지는 위치에 다시 적용하지 마세요. 무시한 메시지는 시험 중 확인할 수 있게 출력하거나 기록하세요.
- 정상 상태와 오래된 상태의 처리 결과를 비교할 수 있는 시험 방법을 준비하고 실행 방법에 기록하세요. 실제 네트워크 장애가 우연히 생기기를 기다릴 필요는 없습니다.
- 예를 들어 A의 위치를 `(3, 5)`로, B의 위치를 `(8, 2)`로 바꾸고 메시지가 정상 수신되면, A 화면에는 상대 B의 `(8, 2)`가, B 화면에는 상대 A의 `(3, 5)`가 표시되어야 합니다. 좌표 값 자체는 시험할 때 자유롭게 바꿀 수 있습니다.
- 같은 피어의 더 큰 순서 번호를 가진 위치가 먼저 적용된 뒤, 작은 번호의 다른 위치를 보내도 표시된 최신 위치가 되돌아가지 않아야 합니다. 같은 번호를 다시 보내는 시험에서도 위치가 바뀌지 않아야 합니다.
- 전송량을 달리한 두 가지 이상의 시험 조건을 직접 정하고, 송신 수·수신 수·오류 또는 누락 관찰값·걸린 시간을 기록하세요.
- 수신하지 못한 데이터를 관찰했다면 그 수치가 무엇을 뜻하는지 적어 주세요. 단순히 아직 도착하지 않은 데이터까지 확정된 손실로 단정하지 마세요.
- 전송량 시험에서도 같은 위치 메시지 규약을 사용하세요. 반복 전송하는 새로운 메시지에는 증가한 순서 번호를 사용하고, 두 피어가 반영한 위치·수신 수를 기록하세요. 손실 메시지의 자동 재전송이나 반드시 도착하게 만드는 기능은 요구하지 않습니다.
- 이 과제는 콘솔에서 통신 원리를 확인하는 별도 프로그램입니다. NGO 코인 게임의 전송 방식을 UDP 직접 구현으로 바꿀 필요는 없습니다.

## 6. 제출 구성

다음과 같이 하나의 폴더로 묶어 제출하세요. 폴더 이름은 예시이며 제출 위치에 별도 규칙이 있으면 그 규칙을 따라 주세요.

```text
이름_GameNetwork/
  README.md
  DESIGN.md
  TEST_REPORT.md
  CoinGame/             Unity 프로젝트 원본
    Assets/
    Packages/
    ProjectSettings/
  UdpPeer/              콘솔 프로젝트 원본
    프로젝트 파일과 소스
  Evidence/             시험 로그·필요한 화면 캡처
```

- Unity의 `Assets`, `Packages`, `ProjectSettings`는 반드시 포함하세요. 씬·프리팹·소스와 연결 정보를 담은 `.meta` 파일도 포함하세요.
- Unity의 `Library`, `Temp`, `Logs`, `Obj`와 자동 생성 캐시는 제외하세요. 콘솔 프로젝트의 `bin`, `obj`도 제외하세요.
- 실행 파일만 제출하지 마세요. 콘솔의 `.csproj` 파일과 소스, 프로젝트를 다시 열고 빌드하는 데 필요한 파일을 포함하세요.
- 필요한 패키지 버전·외부 의존성·복원 방법을 `README.md`에 적어 주세요. 특정 개인 컴퓨터의 절대 경로가 없어도 실행할 수 있게 준비하세요.
- 별도의 실행 빌드가 필요하다고 공지된 경우에는 원본과 구분해 포함하세요. 빌드를 포함해도 프로젝트 원본을 대신할 수는 없습니다.
- 비밀번호·인증 토큰·개인 키 등 비밀 정보와 사용 권한이 없는 리소스는 넣지 마세요.
- 제출 전 다른 위치에 풀어 두 프로젝트를 다시 열고 실행하는지 확인하세요.

### GitHub 저장소 링크로 제출하는 경우

- 파일 대신 **GitHub 저장소 링크로 제출할 수도 있습니다.** 링크로 제출해도 위의 `이름_GameNetwork/` 폴더와 내부 파일·프로젝트 구성을 동일하게 지켜야 합니다.
- 저장소는 **공개 저장소(Public)** 여야 합니다. 별도의 초대나 접근 권한 요청 없이 평가자가 내용을 확인하고 내려받을 수 있어야 합니다.
- 제출한 저장소와 필수 제출 파일은 **과정이 종료될 때까지 공개 상태로 유지하세요.** 그전에 저장소를 삭제하거나 비공개로 전환하거나, 제출 파일을 제거하지 마세요.
- 제출 후에도 평가자가 접근할 수 있도록 제출한 링크를 유지하세요. 저장소 주소를 변경해야 한다면 변경된 링크를 담당 교사에게 알려 주세요.
- 저장소를 새 위치에 내려받은 뒤에도 안내서대로 두 프로젝트를 열고 실행할 수 있는지 확인하세요.

## 7. 평가 기준

평가자는 제출물을 직접 열어 실행하고, 코드·설계·시험 기록이 서로 맞는지 확인합니다. 필요하면 사전 안내된 범위에서 입력이나 실행 조건을 바꾸거나 기능 설명을 요청할 수 있습니다. 화면 캡처나 설명만으로 구현 기능을 모두 인정하지는 않습니다.

NCS의 관련 능력단위요소에 따라 다음 내용을 확인합니다.

| 능력단위요소 | 안내하는 평가 관점 |
| --- | --- |
| 게임 서버 시스템 설계하기 | 요구에 맞는 역할·구조·데이터 흐름, 정보 수집과 선택 근거, 설계와 구현의 일치 |
| 서버 네트워크 프로그래밍하기 | 독립된 프로그램 사이의 실제 송수신, 주소·포트 설정, NGO 접속·종료 및 UDP 양방향 통신 |
| C/S 모델에서의 클라이언트 네트워크 프로그래밍하기 | NGO 요청·서버 판정·결과 수신의 구분, 잘못된 요청 처리, 상태 일치, 전송량과 시험 결과에 대한 판단 |
| P2P 모델의 클라이언트 네트워크 프로그래밍하기 | UDP 피어 간 통신, 송신 피어 구분, 최신 상태 반영, 잘못된 메시지 처리와 전송량 시험 |
| 게임 서버 응용 프로그래밍하기 | 서버 게임 규칙의 실행, 데이터·운영 기록 설계, 종료·재접속 시험, 측정에 따른 조정과 재확인 |

### 평가에서 중요하게 보는 점

- **실제 동작:** 두 실행 환경에서 요청과 결과가 대응하는가.
- **판정의 정확성:** 잘못된 요청·중복 요청이 게임 상태를 잘못 바꾸지 않는가.
- **상태의 일관성:** 참여자에게 보이는 점수·코인·상대 상태가 정한 규칙대로 맞는가.
- **설계와 코드의 연결:** 기능을 어디에서 처리하는지 설명할 수 있는가.
- **확인 가능한 기록:** 조건·수치·실제 결과와 재확인 내용이 남아 있는가.
- **재현 가능성:** 평가자가 안내서대로 프로젝트를 열고 같은 결과를 확인할 수 있는가.

특정 샘플과 코드가 똑같은지, 화면이 화려한지로 평가하지 않습니다. 일부 기능이 부족하더라도 확인 가능한 나머지 기능과 산출물은 구분해 확인합니다.

### 이번 제출 과제의 범위

NGO 게임과 UDP 피어 프로그램을 NCS 관련 지식·기술의 증거로 사용합니다. 다만 이 제출만으로 능력단위의 모든 수행준거가 확인되는 것은 아닙니다.

직접 TCP 모듈 작성, 별도 네트워크 스레드, 암호화 통신 구현, DB 연계 실행, 리포팅·패치 프로그램 구현은 **이번 안내의 필수 제출 기능에 포함하지 않습니다.** 추가 평가는 학습과 사전 안내 후 별도로 실시합니다. 공개되지 않은 고급 기능을 이 과제의 숨은 필수 조건으로 요구하지 않습니다.

# DAY 06: 시스템 기획서 통합과 리뷰

오늘은 6일 동안 작성한 시스템 규칙, 흐름도, 공식, 테이블을 하나의 시스템 기획서로 묶고 리뷰합니다. 시스템 기획의 마지막 목표는 "내가 이해한 문서"가 아니라 "다른 사람이 구현하고 검증할 수 있는 문서"입니다.

## 1. 핵심 개념: "설명서만 보고 조립할 수 있게 만들기"

가구 조립 설명서를 생각해봅시다. 부품 이름, 조립 순서, 나사 개수, 주의사항이 분명하면 처음 보는 사람도 조립할 수 있습니다. 반대로 "적당히 연결한다"라고 쓰여 있으면 사람마다 결과가 달라집니다.

시스템 기획서도 마찬가지입니다. 개발자가 문서만 보고 구현 방향을 잡을 수 있고, QA가 문서만 보고 정상 동작을 판단할 수 있어야 합니다.

### 이 단어는 무슨 뜻인가요?

- **시스템 기획서**: 특정 시스템의 규칙, 흐름, 공식, 데이터, 예외를 정리한 문서입니다.
- **리뷰**: 다른 사람이 읽고 빠진 부분이나 모호한 부분을 찾는 과정입니다.
- **테스트 조건**: 시스템이 정상인지 확인하기 위해 준비해야 하는 상황입니다.
- **수정 이력**: 문서가 언제, 왜 바뀌었는지 남기는 기록입니다.
- **검증 가능성**: 문서 내용이 실제로 확인 가능한 형태로 쓰였는지의 정도입니다.

## 2. 시스템 기획서에 들어갈 기본 구성

최종 문서는 다음 순서로 묶으면 읽기 쉽습니다.

| 순서 | 내용 |
| :--- | :--- |
| 1 | 시스템 이름과 목적 |
| 2 | 핵심 규칙 요약 |
| 3 | 입력과 출력 |
| 4 | 기본 흐름 |
| 5 | 조건 분기와 예외 상황 |
| 6 | 필요한 공식 |
| 7 | 필요한 데이터 테이블 |
| 8 | 테스트 조건 |
| 9 | 남은 위험과 수정 필요 사항 |

## 문서 실습 2: 리뷰 체크리스트

**미션:** 짝의 시스템 기획서를 읽고 아래 항목을 확인합니다.

```text
리뷰 대상 시스템:
리뷰어:

1. 시스템 목적이 한 문장으로 이해되는가?
- 예 / 아니오
- 의견:

2. 입력과 출력이 분명한가?
- 예 / 아니오
- 의견:

3. 조건 분기와 예외 상황이 있는가?
- 예 / 아니오
- 의견:

4. 공식의 예시 계산이 있는가?
- 예 / 아니오
- 의견:

5. 테이블의 ID와 단위가 분명한가?
- 예 / 아니오
- 의견:

6. 개발자가 구현할 때 질문할 만한 모호한 문장
-

7. QA가 테스트할 수 있는 조건
-

8. 가장 먼저 보완할 부분
-
```

### 발표 체크리스트

- 시스템 이름과 목적을 30초 안에 설명할 수 있는가?
- 입력과 출력이 표나 목록으로 정리되어 있는가?
- 정상 흐름뿐 아니라 실패와 예외도 적혀 있는가?
- 공식에는 예시 계산과 상한/하한이 있는가?
- 테이블에는 ID, 단위, 컬럼 설명이 있는가?
- 다른 학생이 읽고 같은 시스템을 떠올릴 수 있는가?

### 생각해보기

1. 시스템 기획서에서 "적당히", "자연스럽게", "좋게" 같은 말이 위험한 이유는 무엇일까요?
2. 리뷰를 받는 것은 문서의 약점을 드러내는 일일까요, 구현 가능성을 높이는 일일까요?
3. 시스템 기획서와 코드 사이에는 어떤 관계가 있을까요?

## 오늘의 정리

- 시스템 기획서는 구현과 검증을 위한 규칙 문서입니다.
- 최종 문서에는 목적, 흐름, 조건, 공식, 테이블, 테스트 조건이 들어가야 합니다.
- 게임 시스템 기획 과정의 실습은 코딩이 아니라 개발자가 구현할 수 있을 만큼 명확한 시스템 문서를 작성하는 것입니다.

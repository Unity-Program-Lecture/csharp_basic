# DAY 16: 통합 테스트와 프로젝트 인수인계

오늘은 다른 사람이 프로젝트를 복원하고 실행할 수 있도록 코드, 빌드 결과물, 학습 기록을 정리합니다. NCS 학습 목표 G1~G9에 해당하는 결과를 모으고, PC·Android·Web의 실습 결과와 iOS 참고 학습 내용을 구분해 기록합니다.

## 1. 핵심 개념: 사용 설명서가 있는 완제품

완성한 프로젝트를 전달할 때는 받는 사람이 다시 실행할 수 있도록 안내해야 합니다. 필요한 도구의 버전, 빌드 순서, 조작법, 알려진 문제를 함께 정리하면 다음 사람이 작업을 이어가기 쉽습니다.

### 이 단어는 무슨 뜻인가요?

- **회귀 테스트**: 수정 후 기존 기능이 여전히 동작하는지 재확인하는 작업입니다.
- **인수인계**: 다음 사용자가 이어서 실행·수정할 수 있도록 결과와 절차를 전달하는 일입니다.
- **재현성**: 같은 조건과 절차로 같은 결과를 확인할 수 있는 성질입니다.

## 2. 실습: 통합 실행

**미션:** 기능을 확인한 하나의 프로젝트 버전을 기준으로 세 플랫폼의 최종 빌드를 만듭니다.

1. Console 컴파일 오류, Inspector 누락 참조, 코인 ID 중복을 확인합니다.
2. 대상 선택 → 해당 콘텐츠 빌드 → Player 빌드 순서를 플랫폼마다 반복합니다.
3. PC 출력 전체, Android APK, Web 출력 전체를 별도 폴더에 둡니다.
4. 일반 빌드에서 이동·수집·종료·재시작·저장·사운드·주소 로드를 확인합니다.
5. 화면 크기·앱 중단·탭 포커스·네트워크 실패 후에도 정책대로 동작하는지 확인합니다.
6. 문제가 생기면 오류를 고친 뒤 해당 환경과 공통 게임 규칙을 다시 테스트합니다.

### 실행해보면

개발 빌드에서는 동작하던 기능이 일반 빌드에서 실패한다면 스트리핑, 파일 경로, 초기화 순서, 콘텐츠 설정을 살펴봅니다. 오류 로그를 단서로 원인을 찾아 수정하고 다시 확인합니다. iOS는 참고 자료를 통해 학습한 내용으로 기록합니다.

## 3. 실습: 전달 자료 묶기

프로젝트에는 Assets의 .meta, Packages, ProjectSettings를 포함합니다. Library·Temp·개인 IDE 캐시는 복원 가능한 생성 자료로 구분합니다. 빌드 결과는 프로젝트 원본과 구분해서 전달합니다. 서명 키·비밀번호·토큰·개인 장치 정보는 제거합니다.

Unity 밖에서 만든 ContentServer도 별도 폴더로 전달합니다. ContentServer.csproj·Program.cs·Content의 JSON을 포함하고 bin·obj와 인증서 개인키는 제외합니다. 받는 사람은 자신의 PC에서 개발 인증서를 준비합니다. README에는 Unity와 서버의 상대 위치, FilesRoot 실행 인수와 HTTPS 주소를 함께 적습니다.

전달 설명에는 다음을 적습니다.

- Editor·패키지·SDK·실행 기기 버전.
- 첫 씬, 입력 구성, Inspector 연결과 빌드 프로필.
- 자료 구조·게임 로직·플랫폼 코드의 역할.
- Addressables 로컬/원격 여부와 콘텐츠 빌드 순서.
- 오류의 재현·수정·재검증 기록.
- 실제 Player 프로파일의 수정 전후 비교.
- 실행하지 못한 환경과 알려진 문제.

[NCS 연결표](NCS_ALIGNMENT.md)의 G1~G9에 자신의 문서, 코드, 로그를 연결합니다. 각 목표에서 설명을 읽고 이해한 부분과 직접 실행해 확인한 부분을 구분해 적습니다.

## 4. 복원 리허설

**미션:** 기존 Library나 생성 번들에 기대지 않고 다른 폴더에서 복원합니다.

1. 학생 작업을 커밋하고 Unity를 닫습니다. 저장소를 다른 폴더에 clone하거나 Assets·Packages·ProjectSettings와 모든 meta를 새 폴더로 복사합니다. Library·Temp·기존 빌드 출력·ServerData는 복사하지 않습니다.
2. Unity Hub에서 복원 폴더를 Unity `6000.6.7f1`로 열고 패키지 설치와 import·컴파일이 끝날 때까지 기다립니다.
3. `Assets/Scenes/PlatformMain.unity`를 열고 누락 스크립트와 Inspector 참조를 확인합니다. StageMain 프리팹의 코인 10개, PlatformControls.inputactions, StreamingAssets/platform-config.json도 확인합니다.
4. 기본 로컬 구성과 Use Asset Database로 Play하여 한 판을 확인합니다. 이어서 대상 플랫폼으로 전환하고 해당 플랫폼의 로컬 콘텐츠와 Player를 새로 빌드합니다.
5. 생성한 Player를 실행해 시작·이동·수집·종료·재시작·저장·45초 설정을 확인합니다. 원격 비교는 별도 설정 기록을 따라 진행하며, 기존 설치·캐시의 영향도 기록합니다.
6. 서로의 설명서를 바꿔 읽고 추가 설명 없이 실행하고 조작할 수 있는지 점검합니다.

복원한 소스와 기존 빌드의 버전을 혼동하지 않습니다. 마지막 기능 수정 뒤 PC·Android·Web의 콘텐츠와 Player를 각각 다시 빌드하고 자신의 실행 결과를 기록합니다. 빌드 성공과 실제 실행은 구분하며, 기기가 없거나 실행하지 못했다면 미확인으로 남기고 보완 계획을 적습니다. NCS 목표는 자신의 요구 사항·설계·오류 해결·측정·인수인계 기록으로 설명합니다.
